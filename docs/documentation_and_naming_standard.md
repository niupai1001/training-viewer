# Training Viewer — 命名、术语、组件说明与变更管理规范

**规范级别：强制。适用范围：需求文档、架构设计、Python/TypeScript 代码、插件、日志协议、实验命名、界面、测试、提交与发布说明。**

> 核心原则：开发者和使用者应当能够仅凭名称与简短说明，判断一个组件是做什么的；不能要求阅读几百行代码才能弄清 `V2`、`P3` 或 `AdapterX` 是什么意思。

## 1. 文字与文档写作要求

1. **中文解释、英文标识**：面向开发与研究的设计文档以完整中文句子解释；代码标识符遵守 Python/TypeScript 约定，使用有意义的英文单词。技术术语首次出现必须说明用途；不能将一连串英语缩写当作解释。
2. **先说作用，再说实现**：每个组件先用一至两句话写清它解决什么问题、接收什么、输出什么，再解释技术选型；不得只列类名/依赖名。
3. **首次出现解释缩写**：例如“服务器发送事件（Server-Sent Events，SSE）”，此后才可以使用 SSE。对非标准缩写原则上禁止创造；标准缩写必须列入术语表。
4. **一句话只表达一个主要判断**：禁止大量以短词堆积的断句，也避免同一问题反复用不同名字叙述；示例代码必须附中文说明，明确预期输入与输出。
5. **概念、实现与实验严格区分**：架构方法名、代码模块名、实验 Run 名和软件发布版本是四种独立标识，不可混用。
6. **示例与事实区分**：所有示例运行指标、日志路径、模型性能均注明“示例”，不暗示已实现或真实实验验证。
7. **避免只写“支持”**：每项需求说明入口、输入、输出、边界、错误行为和至少一个验收例子；缺少这些内容时属于待定需求。
8. **保留可导航结构**：正式文档顶部给出“目标 / 使用方式 / 主要模块 / 关键文件 / 术语”摘要；较长文档提供目录或明确章节标题。

### 必须避免的写法

| 不允许 | 推荐写法 | 为什么 |
|---|---|---|
| “引入 V3 模块，接入 P2” | “加入波长条件化输入编码器，输出特征经维度投影后送入 SegFormer 编码器” | 写清改变了哪里、数据流怎么走 |
| “用 Nrm + Idx + Vw” | “日志标准化 → 指标索引 → 曲线查看” | 读者不必猜测缩写 |
| “优化了性能” | “在同一数据划分与随机种子下，验证 mIoU 由 X 变为 Y，统计方法见测试报告” | 结果必须可验证；X/Y 仅为填写占位符 |
| “改成新版” | “将全文件重读改为基于字节偏移的增量读取；数据库结构不变” | 明确更改内容与影响范围 |
| “Loss 更好了” | “验证损失（validation loss）从 A 下降到 B，比较基于相同训练步数” | 指标、数据和横轴必须明确 |

## 2. 命名必须覆盖的四个层次

### 2.1 产品界面名（给使用者看）

- 使用自然中文名称，如“实验对比”“训练指标曲线”“预测结果对照”“TensorBoard 日志读取器”。
- 页面、菜单、错误提示、图表图例尽量采用用户能理解的名称；鼠标悬停时展示完整定义。
- 如果界面显示 `mIoU`、`F1`、`Step`，须有 tooltip 或指标详情解释其含义、单位和数据范围。

### 2.2 代码标识符（给开发者看）

- Python 文件/函数/变量：小写英文单词与下划线，例如 `standard_log_reader.py`、`read_new_metric_records()`。
- Python 类：驼峰式大写，例如 `StandardLogReader`、`TrainingMetricIndexer`。
- React 组件：PascalCase，例如 `ExperimentComparisonPage.tsx`、`PredictionComparisonViewer.tsx`。
- TypeScript 函数/变量：camelCase，例如 `groupMetricsByTrainingPhase()`。
- 目录：用途明确，例如 `log_readers/`、`metric_indexing/`、`experiment_comparison/`、`artifact_previews/`。
- 命名描述**职责**，不描述模糊的“新、强、优化”或作者昵称。

禁止用 `m1`、`mod2`、`use_v4`、`new_encoder`、`final_final`、`projA`、`helper2` 等作为正式模块名。循环下标 `i`、数学变量和第三方 API 的标准字段属于例外，但不可滥用。

### 2.3 协议/API 字段名（机器读取）

- 已经冻结的协议字段保持不变，例如 `run_id`、`global_step`、`session_id`、`metrics`；不能为“简洁”私自改成 `rid`、`gs`、`sid`、`m`。
- 新公共字段必须采用完整、稳定、明确的 `snake_case`，并在字段表中说明类型、单位、默认值、示例和兼容性。
- 标准术语如 `id`、`json`、`api`、`gpu`、`lr`、`miou` 可以在**已有标准接口**中保留，需在术语表解释；新接口优先使用完整名称，例如 `learning_rate`。禁止同一协议同时使用 `lr` 和 `learning_rate` 表示相同概念但没有统一映射。
- 任何已公开字段的重命名都属于兼容性变更，必须提供读取旧字段的迁移策略和测试，不能静默替换。

### 2.4 实验名称（给研究者比较）

- 运行的唯一身份由 `run_id` 指定；人类可读名称描述模型、关键变量和种子，不用名称承担唯一性。
- 推荐 `name`（展示名）：`SegFormer 基线｜10 波段输入｜随机种子 42`。
- 推荐实验目录名（便于跨平台文件系统）：`segformer_baseline_10band_seed42`。
- 有消融改动时，例如 `segformer_wavelength_embedding_seed42`，并在 `run.json` 的 `config` 中完整记录被更改的组件和参数。
- 不允许仅使用 `USE_V1`、`USE_V2`、`experiment_04` 区分科学实验；历史名称可保留为 `legacy_alias` 或标签，正式名称补充真实差异。
- 复现实验至少追踪：模型架构、输入数据与波段、数据集版本及划分、随机种子、训练超参数、代码提交版本、预训练权重来源以及是否冻结参数（适用时）。

## 3. 组件必须具有“人能读懂的身份卡”

无论是日志读取器、指标曲线组件，还是未来视觉编码器，只要是新增、替换或发生行为变化的独立组件，必须登记以下信息：

| 字段 | 必填内容 |
|---|---|
| 中文名称 | 一眼能看懂的功能名，如“标准训练日志增量读取器” |
| 代码名称 | 稳定英文标识，如 `StandardLogReader` |
| 唯一标识 | 插件 ID 或组件路径，如 `source.standard_training_log` |
| 一句话职责 | 解决什么问题、不负责什么 |
| 使用位置 | 属于哪一层，被哪些组件调用 |
| 输入 | 文件/数据结构、字段、单位、形状（适用时） |
| 输出 | 数据结构、字段、单位、形状（适用时） |
| 核心处理 | 用连续中文描述数据处理的主要步骤 |
| 与旧实现的差异 | 替换/保留/删除了什么，为什么修改 |
| 配置项 | 名称、含义、默认值、允许值、影响 |
| 异常与边界 | 文件缺失、重复数据、错误数据等如何处理 |
| 测试与验证 | 对应的测试用例、验收标准、已知限制 |
| 文档位置 | 组件文档和变更记录链接 |

**深度学习模块附加项**：输入输出张量形状（例如 `[batch, channels, height, width]`），波段/空间分辨率语义，参数是否可训练，是否加载预训练权重，以及对下游模块的依赖。不得只画方框并写一个自造缩写。

在 `docs/components/` 中每个重要组件应有一份说明；模板见 `docs/templates/component_design_template.md`。组件索引应支持从中文名称反查代码文件、从代码文件反查设计目的。

## 4. 版本命名与架构修改规范

- **软件版本**：采用语义版本，例如 `1.1.0`；版本描述软件整体发布状态，不用来命名功能模块。
- **日志协议版本**：由 `schema_version` 记录；当前为 `1.0`。兼容性破坏需要独立升级协议版本和迁移说明。**本文文档版本 1.1 不改变数据协议 1.0。**
- **组件演化**：原则上保持同一个语义名称，使用 Git 记录实现变更。确实不同的算法/数据流必须用其“技术差异”分别命名；不以 `ModuleV2`、`ModuleV3` 代替定义。
- **实验版本**：使用 `run_id` 关联唯一运行，使用 `experiment`/`name` 描述比较维度，使用 Git 提交与配置文件记录复现信息。
- **旧组件**：若仍保留，应明确标识为 `legacy`（旧实现），注明代替它的新组件和移除计划；不能同时存在多个不清楚区别的 `new`、`new2`、`final`。

### 每次改变组件必须回答的六个问题

1. **原来是什么**：旧组件名称、职责与数据流。
2. **现在改变什么**：新增、删除、替换、保留的操作，不能只写“重构”。
3. **为什么改变**：针对哪一项观察到的缺陷或验证假设。
4. **哪些地方受影响**：代码路径、日志协议、数据流、缓存/数据库、界面及训练结果。
5. **如何验证有效**：测试、消融对照、指标、性能和兼容性检查。
6. **如何回退**：回退 Git 提交、配置开关或迁移步骤，是否会造成数据丢失。

发生架构修改时，同一个变更必须同步更新：组件身份卡、架构与数据流图、配置字段说明、测试用例、变更记录。如果模型训练结果发生改变，应明确指出可复现条件与数据来源。变更记录模板见 `docs/templates/change_record_template.md`。

## 5. 图表与架构图要求

- 图上的每一个框使用“中文功能名（代码类名）”，例如“训练指标索引器（TrainingMetricIndexer）”；只有图框面积受限时才使用缩写，但必须紧邻图例。
- 箭头必须表达真实的数据方向；分别标示“输入文件”“解析后的数据”“索引记录”“可视化查询”，不能只写“数据”。
- 对模型结构图，必须标注关键张量形状和训练状态；对系统结构图，标明文件位置、进程边界及读写责任。
- 组件被删除/绕过/替换后应更新图，不能留下不再存在的方框。

## 6. 统一术语表（本项目首批）

| 缩写/词 | 中文解释 | 本项目含义 |
|---|---|---|
| Project | 项目 | 多个相关实验的上层归档 |
| Experiment | 实验组 | 一组围绕同一假设或对照维度的 Run |
| Run | 单次运行 | 一次独立训练/评估执行，可包含多个恢复会话 |
| Session | 执行会话 | 某一次启动训练进程到退出的时间段 |
| Metric | 指标 | Loss、准确率、IoU 等数值记录 |
| Artifact | 实验产物 | 预测图、表格、模型文件等非标量结果 |
| Adapter | 数据格式适配器 | 将一种日志源转换为内部标准记录 |
| Indexer | 索引器 | 增量读取后建立数据库查询索引 |
| TVLP | Training Viewer Log Protocol，训练日志协议 | 本项目制定的标准日志格式 |
| JSONL | JSON Lines，逐行 JSON | 每一行都是独立 JSON 记录的日志格式 |
| API | 应用程序编程接口 | 前后端或插件调用的稳定接口 |
| SDK | 软件开发工具包 | 可选的日志写入辅助库，不是必需安装项 |
| UI | 用户界面 | 浏览器或编辑器里看到的操作界面 |
| SSE | 服务器发送事件 | 服务端向浏览器通知新增记录的实时通道 |
| WAL | 预写式日志 | SQLite 提升并发读写能力的一种模式 |
| REST | 表述性状态转移 | Web 接口设计风格 |
| CSV | 逗号分隔值 | 常见表格日志格式 |
| UUID | 通用唯一标识符 | 推荐生成 `run_id` 的方式 |
| DDP | 分布式数据并行 | 多进程训练方式，通常只由主进程记录日志 |
| LTTB | Largest-Triangle-Three-Buckets，三角面积采样 | 大曲线抽样算法之一；不能用于计算真实最优值 |
| mIoU | 平均交并比 | 分割指标；具体类别与平均方法须另行记录 |
| F1 | F1 分数 | 精确率与召回率的调和平均相关指标 |
| LR | Learning Rate，学习率 | 训练优化器超参数，旧日志可保留 `lr` 键 |
| Step / Epoch | 优化步 / 训练轮次 | 两种不同的训练横坐标，不能混用 |
| Checkpoint | 训练检查点 | 用于保存和恢复训练状态的文件 |
| VSIX | VS Code 扩展安装包 | 用于发布编辑器插件 |

新增术语必须在合并对应功能时补充本表；同一个概念在文档和界面中使用同一个名称。

## 7. 文档与代码评审门槛

一次功能提交或架构修改，只有满足以下条件才算完成：

- [ ] 新组件使用有意义的英文代码名和中文展示名，不依赖 V1/V2 或自造缩写。
- [ ] 新术语在第一次出现时解释，并登记术语表。
- [ ] 新组件具有身份卡，输入输出、数据流与责任边界清楚。
- [ ] 变更记录明确“原实现、现实现、原因、影响、测试、回退”。
- [ ] 代码中的名称、API 字段、界面标签与文档相互对应，若不同则有映射说明。
- [ ] 修改日志协议字段时提供兼容性策略和测试；没有任意重命名已发布字段。
- [ ] 新指标写明计算定义、单位、优化方向和比较前提。
- [ ] 数据流图/架构图与实际实现一致，不能是过时示意图。
- [ ] 更新 README 中用户可见的使用说明、示例和限制。
- [ ] 验收测试覆盖正常、错误和边界情况；不能只写“已测试”。

**评审规则**：任意必填项缺失，则该功能标记为“文档未完成”，不允许宣布设计或实现已经完成。对 AI 编程代理同样适用：新增模块时应同步生成必要文档，不接受只有代码、没有清晰解释的交付。
